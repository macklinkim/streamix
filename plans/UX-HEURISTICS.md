# Streamix UX 수정 조사

조사일: 2026-09-27. `ux-heuristics`의 Nielsen 휴리스틱, Krug의 Trunk Test, 접근성 체크리스트로 공개 화면을 조작하고 주요 흐름의 소스를 추적했다. 이 문서는 초기 조사에서 **수정이 필요한 항목만** 기록했다. 아래 실행 기록은 후속 코드 변경 상태를 구분한다.

## 범위와 판정

- 실제 브라우저에서 `/`의 애니메이션 건너뛰기 → 둘러보기, 검색어 입력·Enter, `/login` → `/signup` 이동, 빈 가입 양식 제출을 확인했다. 검색은 입력값만 남고 결과·경로 변화가 없었다. 가입 양식의 필수 입력 오류와 첫 필드 포커스는 정상 동작했다.
- 2026-09-27 Fly 백엔드 6대(DB·Redis·Core·Chat·Media·BFF)를 복구한 뒤 운영 페이지를 재방문했다. `/`에서 `0개 방송 중`과 빈 상태가 표시됐고, BFF `/health` 및 `ListLive`가 200을 반환했다. 이전의 지속 스켈레톤은 중지된 백엔드 때문이었으므로 제품 결함으로 세지 않는다. 시청·채팅·스튜디오의 수정 항목은 여전히 **소스 경로로 입증된 예상 동작**이며, 실제 방송·로그인 계정으로 재현 검증이 필요하다.
- 잠정 UX 점수: **4/10**. 백엔드 복구 후 홈은 정상적으로 빈 목록을 표시하지만, 검색 무반응, 시청 중단 가능성, 실패 상태 오표시, 채팅 오류 무시가 핵심 과제를 방해한다. 방송 0개라 시청·채팅은 운영 재현 전까지 잠정 판정이다.
- 심각도: **4** 핵심 과제 차단·데이터/자격증명 손실 위험, **3** 주요 과제 실패 또는 잘못된 상태 안내, **2** 반복 마찰·접근성 장애, **1** 사소한 불편. 아래 항목은 재현 가능성과 영향도를 함께 고려했다.

## 수정 항목

### UX-01. 재생 URL 5분 만료 후 방송 시청 중단 가능성 — 심각도 4, 우선순위 P0

**상황:** 시청자가 라이브 방송을 5분 넘게 같은 탭에서 본다. `getPlaybackUrl`은 300초 서명 URL을 발급하지만, 시청 페이지의 playback query에는 주기적 갱신이 없다. 미디어 서버는 만료된 토큰을 403으로 거절하고 플레이어는 같은 URL로만 재시도한다. 창 포커스 전환 등에 따른 우연한 재조회에 의존하므로 연속 시청이 끊길 수 있다. **실방송 재현은 미실시.**

**근거:** `apps/svc-core/src/channel/channel.service.ts:279-294`, `apps/svc-media/src/hls-server.ts:18-24,116-120`, `apps/web/app/watch/[slug]/page.tsx:20-24`, `apps/web/components/player.tsx:25-39`. **휴리스틱:** 시스템 상태 가시성, 오류 복구.

**최소 수정:** 만료 전에 새 playback URL을 받아 플레이어에 전달한다. 실패 시 재시도 상태를 표시하고, 403에서 만료 URL을 무한 재사용하지 않는다. **검증:** 라이브 재생을 6분 이상 유지하고 403 이후에도 새 URL로 자동 회복하는지 확인한다. 만료 시각을 단축한 자동 검사 추가.

### UX-02. 채널·카테고리 검색창 무반응 — 심각도 3, 우선순위 P1

**상황:** 홈 헤더에서 `게임`을 입력하고 Enter를 눌러도 결과, 필터, 경로 변화가 없다. 입력은 검색 기능처럼 보이지만 `<input type="search">`에 상태·제출 처리가 없다. 모바일에서는 이 입력 자체가 숨겨지고 대체 검색도 없다.

**근거:** 브라우저 `/` 입력·Enter 관찰; `apps/web/components/site-header.tsx:64-72`. **휴리스틱:** 시스템과 실제 세계의 일치, 기대에 따른 동작, 발견 가능성.

**최소 수정:** 검색 기능을 연결해 결과·빈 결과·오류를 보여주거나, 구현 전까지 입력을 제거한다. 기능을 유지한다면 모바일에서도 접근 가능하게 한다. **검증:** 채널명·카테고리 검색, 결과 없음, 모바일 키보드 제출을 확인한다.

### UX-03. 채팅 전송 실패를 숨기고 작성 내용을 지움 — 심각도 3, 우선순위 P1

**상황:** 사용자가 메시지를 보낸 직후 입력값이 지워진다. 서버가 속도 제한 또는 전송 실패를 `{type:"error"}`로 알려도 클라이언트가 무시한다. 메시지는 화면에 나타나지 않고 실패 이유·재전송 수단도 없다. 연결이 닫히면 색상 점만 바뀌고 2초 재접속만 반복한다.

**근거:** `apps/web/components/chat.tsx:31-45,60-75,97-110`, `apps/bff/src/ws/chat.ts:324-342`. **휴리스틱:** 시스템 상태 가시성, 오류 인지·진단·복구, 사용자 통제.

**최소 수정:** 서버 오류 코드를 사람이 이해할 메시지로 표시한다. 실패한 초안을 복원하거나 재전송 가능하게 하고 연결 상태를 텍스트로 설명한다. **검증:** 속도 제한·서버 오류·연결 끊김에서 초안과 안내가 보존되는지 확인한다.

### UX-04. 시청 페이지의 오류·오프라인 상태 오표시 — 심각도 3, 우선순위 P1

**상황:** 채널 조회가 네트워크 오류여도 `채널을 찾을 수 없습니다`가 표시된다. 채널이 라이브인데 재생 URL 조회만 실패하면 `오프라인 방송입니다`가 표시된다. 사용자는 실제 원인과 재시도 방법을 알 수 없다.

**근거:** `apps/web/app/watch/[slug]/page.tsx:13-44`. **휴리스틱:** 오류 인지·진단·복구, 시스템 상태 가시성.

**최소 수정:** 존재하지 않는 채널, 채널 조회 실패, 재생 URL 실패, 실제 오프라인을 구별하고 실패 상태에는 재시도 동작을 제공한다. **검증:** 각 API의 404/503/타임아웃과 실제 오프라인을 주입해 문구·재시도를 확인한다.

### UX-05. 스튜디오 조회 오류를 신규 채널 상태로 처리 — 심각도 3, 우선순위 P1

**상황:** 로그인 사용자의 `getMyChannel` 요청이 실패하면 `data`가 없으므로 기존 채널 사용자에게도 채널 생성 양식이 표시된다. 재시도나 장애 안내가 없다.

**근거:** `apps/web/app/studio/page.tsx:266-307`. **휴리스틱:** 시스템 상태 가시성, 오류 예방·복구.

**최소 수정:** 조회 오류를 채널 없음과 별도 상태로 표시하고 재시도를 제공한다. **검증:** 기존 채널 계정에서 조회 503/타임아웃을 주입할 때 생성 양식이 나오지 않는지 확인한다.

### UX-06. 스트림 키 재발급 즉시 적용·확인 없음 — 심각도 3, 우선순위 P1

**상황:** `스트림 키 재발급` 한 번 클릭으로 기존 키가 즉시 무효화된다. 안내 문구는 클릭 버튼 아래에 있고, 새 키는 그 순간만 표시된다. 방송 장비에 이전 키가 저장돼 있다면 이후 송출이 실패할 수 있다.

**근거:** `apps/web/app/studio/page.tsx:124-139,243-254`, `apps/svc-core/src/channel/channel.service.ts:178-191`. **휴리스틱:** 오류 예방, 사용자 통제.

**최소 수정:** 클릭 전에 기존 키의 즉시 무효화·장비 재설정 필요를 확인받고, 성공 후 새 키를 저장할 때까지 볼 수 있게 한다. **검증:** 취소 시 기존 키 유지, 승인 후 기존 키 거절·새 키 표시·복사 확인.

### UX-07. 랜딩 게이트가 공개 탐색·가입을 가림 — 심각도 2, 우선순위 P2

**상황:** 첫 방문자는 전체 화면 애니메이션을 건너뛰어도 로그인 화면에서 다시 `그냥 둘러보기`를 눌러야 라이브 목록에 도달한다. 랜딩 폼에는 회원가입 경로가 없고, 둘러보기 링크는 작은 회색 텍스트다. 공개 방송을 보려는 사용자에게 로그인 필수처럼 보일 수 있다.

**근거:** 브라우저 첫 방문 동선 관찰; `apps/web/components/landing/landing-gate.tsx:12-55`, `apps/web/components/landing/landing-login.tsx:91-127`, 헤더 가입 링크 `apps/web/components/site-header.tsx:37-51`. **휴리스틱:** 사용자 자유·통제, 인지 부담, Trunk Test.

**최소 수정:** 공개 탐색을 첫 단계에서 명확히 제공하고 가입 경로를 랜딩에 추가한다. 애니메이션 건너뛰기와 사이트 진입을 한 동작으로 합칠지 사용자 목표에 맞춰 결정한다. **검증:** 신규 방문자가 로그인 없이 라이브 목록에 한 번의 선택으로 도달하고 가입을 찾을 수 있는지 확인한다.

### UX-08. 랜딩 모달의 라벨·키보드 접근성 미비 — 심각도 2, 우선순위 P2

**상황:** 로그인 화면의 `아이디`, `비밀번호` `<label>`이 입력과 연결되지 않는다. 랜딩 전체 화면 오버레이에는 대화상자 의미, 초기 포커스, 포커스 범위 제한, 닫기 키 처리가 없다. 애니메이션 단계의 로그인 폼이 접근성 트리에 먼저 노출돼 키보드·스크린리더 사용자에게 순서가 혼란스러울 수 있다.

**근거:** 브라우저 접근성 트리에서 애니메이션 뒤의 입력 확인; `apps/web/components/landing/landing-login.tsx:64-86`, `apps/web/components/landing/landing-gate.tsx:31-55`. **휴리스틱:** 접근성, 일관성·표준, 사용자 통제.

**최소 수정:** `htmlFor`/`id`로 라벨을 연결한다. 게이트를 유지한다면 실제 모달 포커스 동작과 배경 비활성화를 구현하고, 닫기·건너뛰기 경로를 키보드로 제공한다. **검증:** Tab/Shift+Tab/Escape와 스크린리더의 필드 이름·포커스 순서를 확인한다.

### UX-09. 클립보드 실패에도 복사 성공 표시 — 심각도 2, 우선순위 P2

**상황:** 스트림 키·주소 복사 버튼이 `navigator.clipboard.writeText`의 성공 여부를 기다리지 않고 체크 아이콘을 표시한다. 브라우저 권한이나 보안 컨텍스트 문제로 복사가 실패하면 방송 설정에 잘못된 값을 붙여넣게 될 수 있다.

**근거:** `apps/web/app/studio/page.tsx:31-45`. **휴리스틱:** 시스템 상태 가시성, 오류 예방.

**최소 수정:** Promise 성공 후에만 성공 표시, 실패 시 안내·수동 선택 경로 제공. **검증:** 클립보드 거부를 주입했을 때 성공 표시가 나오지 않는지 확인한다.

### UX-10. 라이브 목록 조회 실패가 빈 화면으로 남음 — 심각도 3, 우선순위 P1

**상황:** 운영 홈은 현재 정상 조회 결과 `0개 방송 중`을 표시한다. 그러나 조회가 실패하면 홈이 `data`와 `isLoading`만 읽어 오류를 표시하지 않는다. 스켈레톤이 사라진 뒤 방송 수·빈 상태·재시도 없이 화면이 비어, 사용자는 방송이 없는지 장애인지 구별할 수 없다. **장애 주입 재현은 미실시.**

**근거:** 운영 브라우저 `/` 빈 목록 관찰 및 BFF `ListLive` 200; `apps/web/app/page.tsx:24-49`, `apps/web/lib/hooks.ts:7-12`. **휴리스틱:** 시스템 상태 가시성, 오류 진단·복구.

**최소 수정:** 쿼리 오류를 별도 상태로 표시하고 `다시 시도`를 제공한다. 정상 응답의 0개와 실패를 분리한다. **검증:** 목록 API를 503/타임아웃으로 만들었을 때 오류·재시도가 보이고, 복구 후 목록으로 돌아오는지 확인한다.

### UX-11. 빈 라이브 화면의 다음 행동이 방송자에게만 맞춰짐 — 심각도 2, 우선순위 P2

**상황:** 운영 홈에 방송이 0개일 때 `OBS로 송출하면 여기에 바로 표시됩니다`만 보인다. 시청자는 다음에 할 수 있는 행동이나 새 방송이 생겼는지 확인할 방법을 안내받지 못한다. 계정이 없는 방문자에게는 OBS 송출 문구도 즉시 실행할 수 없는 행동이다.

**근거:** 운영 브라우저 `/` 빈 상태 관찰; `apps/web/app/page.tsx:45-49`. **휴리스틱:** 사용자 언어와의 일치, 인지 부담, 다음 행동의 명확성.

**최소 수정:** 시청자에게 `아직 라이브가 없습니다`와 다시 확인할 방법을 먼저 안내하고, 방송 시작 안내는 로그인한 방송자에게만 별도로 제공한다. **검증:** 비로그인 시청자와 방송자 각각에게 실행 가능한 다음 행동이 보이는지 확인한다.

### UX-12. 홈·로그인·회원가입의 브라우저 제목이 같음 — 심각도 2, 우선순위 P2

**상황:** 운영 브라우저에서 `/`, `/login`, `/signup` 모두 `Streamix — 라이브 스트리밍`으로 표시된다. 여러 탭을 열거나 브라우저 기록·보조 기술로 돌아올 때 현재 페이지를 제목으로 구별할 수 없다.

**근거:** 운영 브라우저 세 경로의 제목 관찰; `apps/web/app/layout.tsx:10-13`. **휴리스틱:** 현재 위치 표시, Trunk Test.

**최소 수정:** 경로별 제목을 `로그인 | Streamix`, `회원가입 | Streamix`처럼 지정한다. **검증:** 각 페이지의 탭 제목·브라우저 기록·스크린리더 문서 제목이 구별되는지 확인한다.

## 실행 순서와 검증 한계

1. UX-01: 연속 시청이 중단되지 않게 복구.
2. UX-02~06·UX-10: 검색·채팅·오류 상태·방송 자격증명 같은 주요 과제의 신뢰성 복구.
3. UX-07~~09·UX-11~~12: 첫 방문 마찰과 접근성, 빈 상태·위치 안내 수정.

**10/10 재평가 조건:** 위 12건을 수정한 뒤, 공개 탐색·검색·6분 이상 시청·채팅 실패·스튜디오 장애·키 재발급·키보드 접근·목록 장애 복구를 실제 브라우저에서 통과시키고 빠른 진단 항목을 모두 재검토한다. 이 검증 전에는 10점을 주장하지 않는다.

브라우저 조작으로 확인한 것은 첫 방문·검색·가입 양식, 복구 후 빈 라이브 홈, 로그인·회원가입 페이지의 문서 제목까지다. 실제 라이브 재생, 인증 후 채팅, 방송 장비, 모바일 전체 화면, 스크린리더 및 자동 접근성 검사, 성능 측정은 실시하지 않았다. 이 문서의 소스 기반 예상 동작을 구현 전에 재현 테스트로 확정한다.
